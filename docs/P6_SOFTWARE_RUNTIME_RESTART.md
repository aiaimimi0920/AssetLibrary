## 范围与退出条件

2026-10-06，接续 `0.3.0-dev.26` 的 Capability / 小型应用包传输闭环。新增测试 `tests/software-package-restart.test.mjs`；复用当前完整关闭、持久化 D1/R2 和重新获取 binding 的测试夹具，不新增恢复开关、生产旁路或另一套存储实现。

本轮只证明受控本地完整关闭与重开，不是突然崩溃、云灾备、实际账号、原生 AV 安全或完整 P6 生产退出。软件载荷不执行；AV、身份为合成测试事实，正向分发由宿主直接调用现有业务核心假设部署准入。实际 HTTP Worker 的 `SCANNER_CLOUD_NOT_VALIDATED` 门禁在重开后仍硬拒绝。

## 可观察证明

两种类型各有两个独立测试，使用新的隔离持久目录：

1. 两个软件包检查任务入队后取消其中一个，关闭全部旧运行时并复用原目录重开。D1 全业务表、审计、回执、Schema 和保留对象的字节/ETag 与关闭前一致；取消对象不复活。
2. 调度队列时只对有效包调用一次合成 AV。取消上传关联的检查转为 `invalidated`、attempts 为 0、result 为 null；它不是 `cancelled` 检查状态。再次调度不增加成功审计或执行次数。
3. 有效包经真实格式检查、版本创建和独立审核后再次重开，检查与批准的完整 API 事实保持。所有旧实例、旧 D1 stub 及旧监听地址都验证不可再用；重新取得 D1/R2 binding，不重放迁移、不重置状态。
4. 假设准入发布并授予下载权限，重开后同一个有效短期票据仍能取得完整字节和 Range，完整摘要与发布事实一致，资源库类型正确。
5. 撤销授权后重开，资源库为空、旧票据拒绝。再次授予授权不会复活旧票据，只能申请新票据。
6. 下架后第三次重开，资源库仍为空，新票据也拒绝。owner 历史发布事实为 `unlisted` revision 2，R2 原字节保留。

每次重开均逐表比较真实 D1 快照，逐对象核对 ETag 和原字节。Windows 额外记录当前测试 Node 的 workerd 子进程：关闭前仅一个、关闭到重开之间为零、重开后为新的一个；不停止其他会话或手测运行时。两种类型合计十次完整重开。

## 首轮问题与验证边界

首轮四项测试中两项失败，原因是把上传的 `cancelled` 状态误用作检查任务状态。真实源码规定失效绑定在调度时记录 `invalidated`，所以只修正测试并增加 attempts/result/审计及调用次数断言，不把错误预期改造成生产行为变更。首轮日志保留，不称一次零失败。

新测试单文件 150 有效代码行，无新增超限例外。格式、类型、行数和 `git diff --check` 通过；新测试 4 项与直接邻近回归合计 17 pass / 0 fail / 0 skip。完整 suite 交由当前提交的 GitHub CI 再次验证，不把上一轮 281 项本地结果冒充本轮完整结果。生产源码、Schema、依赖、身份合同和部署配置均未改变；继续使用 `.26` 运行时版本，不伪造新生产能力。
